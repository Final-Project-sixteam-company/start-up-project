## Summary

QA 환경:

```text
FE: Flutter Android debug APK
Device: Android Emulator Pixel_10
API: https://api.clueroom.xyz
Scenario: CL-011 스튜디오9
Session: QA 중 신규 생성한 PLAYING 세션
```

전체 판정:

```text
Android E2E 실행: 가능
시나리오 목록/상세 진입: 통과
세션 생성/브리핑/대시보드 진입: 통과
증거 조회/상세/이미지 확대: 통과
용의자 목록/상세/심문: 통과
증거 제시 플로우: 동작하나 UX 개선 필요
타임라인 화면: 미제공
최종 추리 제출/결과 조회: 통과
시나리오/AI 답변 품질: 개선 필요
API 스포일러 메타데이터: 수정 필요
```

## QA Method

이번 QA는 정답 문서나 seed를 보지 않고 진행했다.

진행 방식:

```text
1. 앱 온보딩 후 시나리오 라이브러리 진입
2. 스튜디오9 상세/브리핑 확인
3. 초기 증거와 용의자 기본 진술 확인
4. 증거 기반으로 질문 순서 결정
5. AI 심문과 증거 제시를 반복
6. 앱에서 노출된 정보만으로 최종 추리 제출
7. 결과 화면 기준으로 플레이 경험과 개선점 정리
```

플레이어 관점의 추리 전략:

```text
1. 사건 구조를 "물리 조작 + 목격 공백 + 움직임 유도"로 가정
2. 핵심 장면의 위치/지시/기술/안전 계열 접근권한을 비교
3. 시간대와 접근권한이 충돌하는 용의자 답변을 찾음
4. 핵심 증거를 용의자에게 제시해 반응을 확인
5. 최종 추리에서 범인/동기/방법/은폐를 제출
```

최종 제출 결과:

```text
제출: 완료
채점/등급: private artifact
정오 여부: private artifact
세부 breakdown: private artifact
```

정답 세부와 결과 정오는 공개 문서에 남기지 않는다.

## Good

### 1. 첫 진입과 사건 목표는 명확함

상세/브리핑에서 사건 구조는 비교적 잘 전달된다.

좋았던 점:

```text
피해자가 공개된 cue 직후 사고 발생
짧은 과노출로 목격 신뢰도가 낮음
위치/지시/기술/안전/기록 계열 단서가 수상함
플레이 목표가 "범인, 방법/동기, 결정적 증거 3개"로 제시됨
```

플레이어가 초반에 잡을 수 있는 합리적 가설:

```text
단순 추락 사고가 아니라,
장비/위치/큐를 이용해 피해자의 마지막 움직임을 만든 사건이다.
```

### 2. 증거 카테고리와 용의자 직책 연결은 좋음

증거와 용의자 직책이 자연스럽게 연결된다.

예:

```text
기술 담당자 -> 장면 설정/시야 조건
안전 담당자 -> 안전장치/점검표
지시 담당자 -> 장면 지시/최종 블로킹
출연자 -> 위치/대기 흐름
기록 담당자 -> 연속성/기록 백업
```

이 구조는 플레이어가 "누구에게 무엇을 물어봐야 하는지"를 추론하게 만든다.

### 3. 결과 화면은 제출 후 피드백 경로를 제공함

최종 제출 후 결과 화면과 API는 정상적으로 도달했다. 항목별 정오와 세부 breakdown은 private artifact로 분리한다.

장점:

```text
결과 화면 진입 확인
제출 후 피드백 경로 확인
결과 조회 API도 정상
```

## Issues

### P0. API에 추리 스포일러 메타데이터가 노출됨

확인:

```text
GET /api/play-sessions/{sessionId}/evidences
-> importance: FAKE 노출

GET /api/play-sessions/{sessionId}/suspects
-> culpritEligible=false 노출
-> portraitImageUrl path에 RED_HERRING / WITNESS 포함
```

영향:

```text
클라이언트/API 응답만 보면 레드헤링 증거와 비범인 후보를 추릴 수 있다.
추리게임의 핵심 경험이 깨진다.
앱에서 숨기더라도 네트워크 응답/로그/디버그 빌드에서 노출된다.
```

개선:

```text
클라이언트 응답에서 importance=FAKE 제거
클라이언트 응답에서 culpritEligible 제거
asset path에 RED_HERRING / WITNESS / CULPRIT 등 역할성 네이밍 제거
서버 내부 판정용 필드는 DTO 분리
앱에 필요한 라벨은 NORMAL / CORE 정도의 공개 가능한 값만 제공
```

### P1. AI 답변이 너무 회피적이라 심문이 추리 도구로 약함

반복 패턴:

```text
"정상 절차였다"
"누가 바꿨는지는 모른다"
"아직 단정할 수 없다"
"다른 증거와 함께 봐야 한다"
```

문제:

```text
용의자가 방어적으로 말하는 것은 자연스럽다.
하지만 현재 답변은 플레이어에게 다음 질문 방향을 거의 주지 않는다.
증거 제시 후에도 새 정보가 추가되지 않는 경우가 많다.
심문이 "정보 획득"보다 "설명 반복"처럼 느껴진다.
```

실제 관찰 예:

```text
기술 담당자에게 장면 설정 변경을 물음
-> 정상 촬영 준비였고 누가 설정을 변경했는지 모른다고 답변

지시/대본 관련 용의자에게 핵심 시각 증거 제시
-> 공식 대본과 다른 지시인지 아직 단정할 수 없다고 답변

기록 담당자에게 백업 드라이브 제시
-> 원본 보존용이며 다른 증거와 함께 봐야 한다고 답변
```

개선:

```text
증거 제시 답변은 최소 1개 이상의 "새로운 비교 기준"을 제공한다.
예: "내가 승인한 문구는 A까지다", "저 장비는 내 담당이 아니다", "그 시간 이후 접근자는 B/C였다"

각 용의자별 답변 정책에 다음을 명시한다.
- 인정 가능한 사실
- 회피해야 하는 사실
- 증거 제시 시 반드시 제공할 다음 단서
- 모순 압박 시 바뀌어야 하는 태도
```

권장 답변 형태:

```text
나쁜 답변:
"그건 저도 모릅니다."

개선 답변:
"제가 확인한 건 Cue 9 기본 세팅까지입니다. 현장 전환 직후 표시된 문구/신호는 제 승인본과 다릅니다."
```

정답 원문을 노출하라는 뜻이 아니다. 플레이어가 다음 증거로 이동할 수 있는 연결고리를 줘야 한다.

### P1. 시간 답변에 모순처럼 보이는 부분이 있음

관찰:

```text
안전 담당 용의자:
- "리허설 직전 안전장치 확인 때 피해자를 봤다"
- "밤 10시 이후에는 대기실에서 장비 정리만 했다"
```

문제:

```text
사건 기준 시각과 리허설 직전 시각을 모르는 사용자는 두 답변을 모순으로 받아들일 수 있다.
실제 모순이 아니라면 시각 표현을 더 구체화해야 한다.
실제 모순 유도라면 그 모순을 검증할 증거/타임라인이 필요하다.
```

개선:

```text
"밤 10시"처럼 넓은 시간 질문에는 정확한 이동 구간을 답하게 한다.
예: "22:00~22:35는 장비 정리, 22:43에는 안전장치 확인으로 현장에 올라갔다"

용의자별 time window를 response policy에 고정한다.
AI가 임의로 시간대를 뭉개지 않게 한다.
```

### P1. 타임라인 화면이 준비 중이라 추리 난이도가 불필요하게 상승

확인:

```text
앱 타임라인 탭:
"타임라인 준비 중"
```

문제:

```text
스튜디오9는 시간 순서가 핵심이다.
22:18, 22:28, 22:43, 22:47 전후 사건을 비교해야 한다.
타임라인이 없으면 AI 답변의 시간 모순/정합성을 검증하기 어렵다.
```

개선:

```text
MVP 최소 타임라인이라도 제공
증거 detail의 related timeline을 한 화면에 모아 표시
잠긴 증거와 연결된 타임라인은 스포일러 없이 마스킹
각 용의자 심문 화면에서 관련 시간대 quick filter 제공
```

### P1. 핵심 이미지 증거 판독이 모바일에서 어려움

관찰:

```text
지시/시각 계열 핵심 이미지가 모바일 화면에서 흐리게 보임
이미지 확대 후에도 문구 판독이 쉽지 않음
상세 설명에는 실제 판독 결과가 충분히 텍스트화되어 있지 않음
```

문제:

```text
핵심 추리가 이미지 안의 작은 글자 판독에 과하게 의존한다.
사용자가 중요한 단서를 놓칠 수 있다.
```

개선:

```text
핵심 이미지 증거는 "판독 결과" 섹션을 별도로 둔다.
예: "판독 가능한 문구/표시", "공식본과 다른 지점", "비교해야 할 증거"

이미지 안 작은 텍스트는 앱 상세 설명에서 접근성 텍스트로 제공한다.
확대 뷰에서 pinch zoom 또는 crop highlight 지원을 검토한다.
```

주의:

```text
정답 수법을 그대로 말하라는 뜻이 아니다.
이미지에서 실제로 보이는 텍스트/표식은 사용자가 읽을 수 있게 해줘야 한다.
```

### P1. 증거 해금 흐름이 설명 없이 급격하게 변함

관찰:

```text
초기: 8/35
심문/시간 경과 후: 29/35
추가 진행 중: 35/35
```

문제:

```text
증거가 왜 열렸는지 앱에서 명확히 설명하지 않는다.
사용자는 "내 질문 때문에 열린 것인지", "시간 때문에 열린 것인지", "세션 복원 때문인지" 알기 어렵다.
```

개선:

```text
증거 해금 toast/snackbar에 이유 표시
예: "시간 경과로 새 증거 6개 해금", "증거 제시로 관련 증거 2개 해금"

대시보드에 최근 해금 내역 표시
증거 목록에 "방금 해금" 배지 제공
```

### P1. 증거 설명이 "함께 봐야 한다"로 반복되어 방향성이 흐려짐

반복 패턴:

```text
"다른 증거와 함께 봐야 한다"
"별도 증거가 필요하다"
"단독으로 결론을 내리기 어렵다"
```

문제:

```text
논리적으로는 안전하지만 사용자에게는 다음 행동이 모호하다.
35개 증거 중 무엇과 함께 봐야 하는지 계속 직접 찾아야 한다.
```

개선:

```text
각 핵심 증거에 "함께 볼 증거"를 2~3개 명시
각 증거에 "이 증거로 물어볼 대상"을 1~2명 명시
증거 상세 하단 CTA를 "관련 증거 보기" / "관련 용의자 심문"으로 분리
```

예:

```text
현재:
"안전장치 클로즈업과 마모 흔적을 함께 확인해야 한다."

개선:
"함께 볼 증거: 안전장치 확인 사진, 마모 흔적, 안전 점검표 덮어쓰기 흔적"
"물어볼 대상: 안전 담당 용의자"
```

### P2. 증거 제시 UX가 번거로움

관찰:

```text
증거 제시 버튼 -> 35개 증거 선택 목록
검색 없음
최근 본 증거 없음
관련 증거 우선 정렬 없음
증거 선택 후 바로 제시가 아니라 상세 확인 후 "이 증거 제시하기"를 다시 눌러야 함
```

문제:

```text
플레이어가 방금 본 증거를 특정 용의자에게 제시하려 해도 찾는 비용이 높다.
증거가 많을수록 심문 흐름이 끊긴다.
```

개선:

```text
증거 선택 모달에 검색 추가
최근 본 증거 5개 상단 고정
현재 용의자와 관련된 증거 우선 정렬
증거 상세에서 "이 증거 들고 심문하기"를 누르면 선택 상태 유지
심문 화면 상단에 "제시 중인 증거" 표시
```

### P2. 의심도 UI가 실제 추리 진행과 분리되어 보임

관찰:

```text
심문 7회, 증거 35/35 상태에서도 주요 의심도 값이 초기값처럼 유지됨
일부 용의자는 증거상 중요해 보여도 15% 그대로 표시됨
```

문제:

```text
사용자는 의심도가 동적으로 갱신된다고 기대할 수 있다.
실제로 고정값이라면 잘못된 힌트처럼 보인다.
```

개선:

```text
동적 갱신이 아니면 "초기 의심도" 또는 "경찰 초기 판단"으로 라벨 변경
동적 갱신을 할 예정이면 증거/심문 결과에 따라 변경
레드헤링/비후보를 암시하지 않도록 수치 설계 재검토
```

### P2. Android 디버그 실행 시 알림 권한 다이얼로그가 첫 진입을 막음

관찰:

```text
앱 splash 후 Android notification permission dialog가 표시됨
권한 처리 전에는 홈 화면 진입이 막힌 것처럼 보임
```

영향:

```text
QA 자동화 시 앱이 멈춘 것처럼 오해 가능
첫 사용자 경험에서도 온보딩 전에 시스템 권한이 먼저 뜨면 흐름이 끊김
```

개선:

```text
온보딩/홈 진입 후 적절한 시점에 알림 권한 요청
```

## Scenario / Content Improvement Proposal

### 1. 핵심 수법 이해를 위한 단서 레이어를 명확히 나누기

현재 플레이어가 봐야 하는 층위:

```text
동기
위치 조작
시청각 큐
목격 공백
안전장치/물리 실패
은폐/기록 조작
```

권장:

```text
각 층위마다 대표 증거 1~2개를 명시적으로 세운다.
각 층위의 레드헤링은 "왜 레드헤링인지" 후반 증거에서 정리되게 한다.
```

### 2. AI 답변 정책에 "정보량 단계"를 둔다

현재:

```text
기본 질문과 증거 제시 질문의 정보량 차이가 약함
```

권장 단계:

```text
FREE 질문:
짧은 알리바이/관계/기본 방어

증거 제시:
해당 증거의 소유/접근/시간대 중 하나를 구체적으로 언급

모순 압박:
기존 진술과 충돌하는 지점을 일부 인정하거나 다른 용의자/증거로 시선 이동

핵심 증거 제시:
정답을 직접 말하지 않되, 플레이어가 다음 결론으로 갈 수 있는 결정적 경계 제공
```

### 3. 용의자별 "절대 흔들리면 안 되는 시간표" 작성

AI 모순을 줄이려면 각 용의자에게 시간표를 고정해야 한다.

필요 데이터:

```text
21:45~22:47 주요 이동
마지막으로 피해자를 본 시점
사건 순간 자신이 있던 위치
본 것 / 보지 못한 것
접근 가능 장비
거짓말 가능한 범위
증거 제시 후 인정 가능한 범위
```

특히 "마지막으로 봤다"와 "그 이후 어디 있었다" 답변은 같은 시간표에서 생성되어야 한다.

### 4. 증거 상세에 "사용자용 판독 결과" 추가

각 핵심 증거에 다음 섹션 추가를 권장한다.

```text
관찰 정보
판독 결과
함께 볼 증거
물어볼 대상
주의할 오해
```

예:

```text
판독 결과:
이미지에서 확인 가능한 표식/문구/손상 방향을 텍스트로 설명한다.

함께 볼 증거:
증거 A, 증거 B, 증거 C

물어볼 대상:
관련 용의자 1~2명
```

## Backend / API Improvement Proposal


권장 공개 값:

```text
Evidence public label:
- NORMAL
- CORE
- LOCKED

Suspect public metadata:
- name

- suspicionLevel
- interrogationCount
```

비공개 유지:

```text

```

예:

```json
{
  "recentUnlocks": [
    {
      "evidenceId": 268,
      "title": "증거명",
      "reason": "TIME_PHASE",
      "triggeredBy": "10분 경과"
    }
  ]
}
```

### 3. Interrogation response에 "answer quality guard" 추가

AI 답변 후 서버에서 최소 품질을 검사한다.

검사 예:

```text
답변이 1~2문장인지
질문/증거와 직접 관련된 명사를 포함하는지
"모른다/단정할 수 없다"만 반복하지 않는지
새로운 비교 기준이 하나 이상 있는지
용의자 시간표와 충돌하지 않는지
```
